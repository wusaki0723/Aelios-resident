# 测试

住户的测试分两种：要起本地 Worker 的（`test/run.mjs`，按阶段跑），和不用起 Worker、直接测某一块代码的（`test/*.mjs`）。服务商、Telegram、企业微信、Aelios 全是假的，不花钱，也不用登录 Cloudflare。

## 怎么跑

```sh
npm install
node test/mock-server.mjs &                                    # 假 Telegram、假企业微信转发机和假 Aelios，端口 9999
NO_PROXY=127.0.0.1 npx wrangler dev --config wrangler.test.jsonc --port 8787 &
NO_PROXY=127.0.0.1 node test/run.mjs main
```

`wrangler.test.jsonc` 用脚本模型（`FAKE_MODEL=true`），回什么由 `src/fake-model.ts` 按你发的话决定。测试什么钟点都可能跑，所以它把 `QUIET_HOURS` 设成 `off`，要测夜里别问的阶段自己在设置页填一段包住当前时间的时段。

`test/run.mjs` 后面跟阶段名，每个阶段要一个刚起的 Worker（先删 `.wrangler/state`）。有的阶段要带变量起 Worker，见 `test/run.mjs` 开头：

## 缓存历史视图回归

`node test/cache-history.mjs` 30 项通过。测试使用合成消息，不使用真实聊天或付费模型。导入实际安装的 `agents/chat`，提取 Think 的真实边界算法，复现内部 UI 消息从 35 增至 37 时，旧工具结果由 3261 字符变成 500 字符、破坏缓存前缀的问题。新 helper 验证跨多轮追加和回合内工具步骤保持相同前缀，只在新窗口选择缩减范围；工具参数、普通聊天文字、原始媒体和工具输出不被覆写。大 JSON、错误与多媒体普通工具结果的预览有 500 字符上限，供应商原生执行的结果保留原结构。

窗口测试执行从 Resident 提取的真实方法，使用文件型 Node SQLite，覆盖数据库关闭重开、1h/5m 过期、持续使用数小时不换窗口、letter 旧视图、fold 后换视图、边界摘要校验，以及恢复中 letter 在 `getTools()` 阶段也不提前开新窗口。它们不等同于完整 Worker 在写信中途被杀的恢复测试。

## 本轮 SDK 与恢复边界

Think 最新仍为 `0.21.0`，没有伪造一个版本升级；底层 agents 从 `0.29.0` 更新到兼容的 `0.30.1`。已核对新版本的 Sessions 实现与旧版逐字一致，升级本身并不修复覆盖层装载问题。新版 Lifecycle 包含启动失败时为排队任务补唤醒、释放被驱逐对象的上下文等修复；真实 Scheduler/Lifecycle 恢复夹具已重新核对并锁到 `0.30.1`，没有移除版本断言。

启动恢复测试运行提取出的实际 Resident 方法和文件型 SQLite，但排程与 DO 边界是替身，不等同于完整 workerd 启动。启动时排程失败会保留任务和日志，后续启动可重试；没有声称新增了保证立即恢复的重试定时器。重定向测试用 Node 的真实 fetch 与本地 HTTP 服务，不冒充 workerd 行为。

闹钟只在模型回合成功完成后重启闲置周期，包含 `SKIP`；它仍是系统备注。重复闹钟可以开启新周期，所以“每周期最多三次心跳”不是整个应用永久只有三次模型调用。仍受既有闹钟日额度限制，不无限扩展心跳次数。

新信的完整有效历史按覆盖层规划后检查和装载，不以删除原文、恢复默认破坏性媒体淘汰、虚报字节数或无限装载绕开限制。真正超限的未收起内容、超大旧信摘要和不完整分支仍拒绝新模型整理。辅助提示清理只按原始行元数据定位那一问一答，不先读取整段正文；已生成信件的恢复只检查完整分支、覆盖层与原范围的元数据，即使后来追加内容超限也能提交旧范围，新增正文不被误收进旧信。写信预算复核只作用于当前实际模型输入是写信提示的回合，不因存在旧 job 就阻挡普通有界聊天。写信继续使用缓存窗口的缩略表示；本轮没有悄悄改成展开所有旧图和工具正文、牺牲写信缓存的模式。原始数据保存和交接信内容完整复刻是不同保证。

### 复审后的修正

- 每次读历史只取一次元数据快照，整条分支从走 9 遍降到 3 遍（行统计、到根检查、正文读取）。删去 4 条、改写 1 条模拟“SDK 读取途中被写入”的测试：DO 里 SQLite 读取是同步的，这种交错不会发生；读出后对消息 id、摘要和实际字节的核对保留。
- “必须确认完整分支”只用于写信准入和恢复已写好的信。分支超过 SDK 的 1 万层或缺父行时，`/status`、网页历史和普通聊天照常读最近一段（与 SDK 相同），写信失败并给出单独的原因；`/status` 和网页历史改用模型实际装载的有界读取，不再整段读取。
- 心跳提示不再建议定闹钟，避免“心跳定闹钟、闹钟重开周期”互相续命；脚本模型改看是否有 `set_alarm` 工具，心跳里定闹钟的一小时限制照测。
- 带 key 的 Aelios 请求一律不跟随重定向；启动恢复日志带错误类型；「重试同步」只在当前目标有可重发的信时出现。

## 交接信新规则的回归

此前回归记录为类型检查，以及 `main` 33 项、`idle` 5 项、`heartbeat` 7 项本地 Worker 集成检查；独立测试 `fold.mjs` 12 项、`letter-config.mjs`、`letter-recovery.mjs` 15 项和原 `web-ui.mjs` 13 组通过。每个 Worker 阶段使用独立的本地状态目录。这些是此前记录，不代表本轮 UI 改动重新运行了上述全部检查。

自动写信须同时满足当前携带聊天达到 token 门槛、闲置到点。写后按完整问答保留最近约 8000 token 原始聊天；最近一轮本身超限时整轮保留。覆盖范围如下。

- 设置校验覆盖默认 `LETTER_TOKEN_THRESHOLD=30000`，只接受大于 `8000` 的整数，`8000`、更小的值、小数、空白以外的非数字、`Infinity`、`1e309` 都应拒收；清掉网页设置后按 Cloudflare 同名变量或默认值取值。旧 `KEEP_RECENT_TOKENS` 的网页存值和环境变量均忽略，不能迁移成门槛，配置列表不再返回旧字段。
- 门槛按当前携带聊天估算，旧交接信、工具调用和结果、图片要计入，人设、工具定义和历史思考不计入。写信收起旧聊天后，按剩下携带的内容重新判断，不能按累计总量触发。
- `idle` 阶段用 `--var LETTER_IDLE_MINUTES:0.05` 把闲置时间缩到 3 秒。未达门槛时闲置也不写；达到或超过门槛但仍连续聊天时不立即写；停止聊天并闲置到点后才写。写信不发 Telegram，记进 Aelios，网页能看信，写信提示那一问一答撤掉，缓存前文和标记保持原有规则；写完没有新聊天就不反复写。
- `heartbeat` 阶段用 `--var LETTER_IDLE_MINUTES:0.05 --var LETTER_TOKEN_THRESHOLD:100000 --var ALARM_MINUTE_SECONDS:0.05`。聊天未达门槛时，即使已经有超出近期保留范围的旧内容，闲置到点仍走原心跳逻辑；次数上限、SKIP、说话后重置、缓存路径限制、心跳里定闹钟的限制都照旧。满足写信双条件且有旧内容时只写信，不问心跳。
- 手动 `/handoff` 在未达门槛时也能写，但要有旧内容可收；只有近期保留范围内的内容时不调模型、不写空信。
- `fold.mjs` 验证固定保留最近约 8000 token 原始聊天，从用户整轮起点保留，不拆连发消息、回复和工具调用链。最近一轮本身超过 8000 时整轮保留；其他情况下不为一条很短的回复额外拉入上一条大段用户消息。最早三条不再额外永久保留，交接信、人设、工具定义另算，旧信不被当成原始近期聊天重复收取。
- `node test/web-ui.mjs` 不用起 Worker，检查 `LETTER_TOKEN_THRESHOLD` 出现在「思考和交接信」且不藏在「更多设置」，默认提示为 `30000`，沿用普通输入、保存和清掉流程；页面没有 `KEEP_RECENT_TOKENS`，并写明双条件、连续聊天不立即触发、固定近期保留量和手动写信限制。

- `letter-recovery.mjs` 用真实 `agents/sessions` 和 Node SQLite 复现旧恢复路径让两封信并存的问题，验证第二、第三封恢复时只携带新信，旧版永久保留的开头三条可被收起（包括新区间终点在旧信之前时也扩展终点替换旧信），重开存储后重试幂等，读写失败不吞异常。这里测的是恢复 helper 的真实持久化行为，不等同于完整 Worker 在写信途中被杀的端到端测试。

## 写信失败与 Aelios 同步回归

本轮已通过类型检查、20 组独立测试、主流程 33 项、闲置写信 5 项和心跳 7 项。新增 `letter-state.mjs` 14 项、`letter-delivery.mjs` 8 项、`letter-recovery-schedule.mjs` 2 项，`web-ui.mjs` 17 组；`node test/letter-failures.mjs` 6 项故障集成检查通过，另有 `restart-1`、`restart-2` 两阶段实际重启 Worker 后补送检查通过。均使用本地假服务，没有调用付费模型。

UI 按以下合同读取状态，写信结果与送达结果互不替代。

- `GET /web/letter` 返回 `{ write, delivery }`。`write` 为 `null` 或 `{ state, at, error? }`，状态为 `writing`、`recovering`、`written`、`empty`、`failed`。
- `delivery` 包含 `pending`、`failed`、`blocked` 数量和 `latest`。`latest` 为 `null` 或 `{ id, at, status, attempts, lastError, sentAt }`，状态为 `pending`、`sent`、`failed`、`blocked`。
- `POST /web/letter/retry` 返回同结构，显式重试当前配置目标下失败或暂停的发送，不重写信、不调用模型；外部目标的状态和预算保留，配置缺失时不重置。目标不匹配仍须返回暂停状态，不将旧信送往新目标。

`web-ui.mjs` 直接运行页面的真实 JS 函数，并静态检查 Alpine 文本绑定，不需要 Worker 或浏览器。新增检查覆盖五种写信状态与未知状态，区分失败、无内容和恢复任务；最近写信时间和错误；四种发送状态、尝试次数和确认时间；待发送、待重试及暂停计数；即使最近一封已送达，只要有旧失败/暂停任务仍显示重试入口；缺省字段和无效数值容错。错误内容用含 HTML 标签的样例验证原样作为文本保存，并检查面板使用 `x-text`、不使用 `x-html`，不把后端安全中文错误拼入 HTML。

接口检查覆盖打开配置、保存或清掉配置后读取 `/web/letter`；状态读取失败不误报配置保存失败，也不把旧状态改成「没有内容」；重试只发 `POST /web/letter/retry`，不发写信请求；防止重复点击和保存目标配置时重试；暂停结果不误报送达，网络失败保留现有状态和重试入口。

后端覆盖如下。先按上面的命令启动假服务和本地 Worker，运行 `node test/letter-failures.mjs`；重启补送测试需在全新状态目录运行 `node test/letter-failures.mjs restart-1`，保留该目录和假服务，重启同一个 Worker 后运行 `node test/letter-failures.mjs restart-2`。独立测试用 `node test/letter-state.mjs`、`node test/letter-delivery.mjs`。

- 写信失败不删除旧聊天；`/handoff` 分别报告无内容、写信失败和已有恢复任务，不把失败混成没有内容，不重复启动恢复任务。
- 已写好的信与同步任务持久化保存；pending 首次立即发送，最多自动尝试 6 次，退避间隔依次为 30 秒、2 分钟、10 分钟、30 分钟、2 小时；耗尽后保留失败任务，手动重试所有失败/blocked 项，不重新调模型写信。
- 移除 Aelios 配置、改地址或 namespace 时先暂停；手动重试再次核对原目标，不匹配则仍 blocked，旧信不流向新地址或空间；key 轮换后可用新 key 向原目标重试。
- 后端错误只返回安全中文，不泄露 key、响应原文或私密目标数据。UI 的 `x-text` 绑定不代替后端脱敏。
- `sent` 要求收到有效 `message_ids` 保存凭据；空的 2xx、无效 JSON、无消息 ID 都不标为成功。当前公开 Aelios 接收接口不去重，重试存在重复原文的风险；固定请求追踪 ID 不提供接收端幂等，也不代表后台记忆提取完成。

实际 Worker 重启用例覆盖首次发送 503 后的待投递任务恢复，验证原信件 ID、正文、尝试次数延续，并且不重新调用模型。尚未覆盖在模型生成、服务端已保存但响应未返回、或本地压缩提交瞬间强制终止 Worker 的完整端到端用例；相关存储边界另由 SQLite/helper 测试覆盖。
